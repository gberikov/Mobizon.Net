Запросы к API с ключом, отправка SMS, аудит CVE зависимостей и нагрузочное тестирование не проводились. Контрактные расхождения без live-проверки отмечены отдельно. P1 — исправить до релиза; P2 — значимый дефект или пробел контракта.

1. **[P1] Placeholder может незаметно заменить номер получателя.**

   [CampaignService.cs:362](../../src/Mobizon.Net/Services/CampaignService.cs#L362): сначала записывается `Recipient`, затем словарь `Placeholders` записывается в то же пространство ключей. `Recipient="77001111111"` и `Placeholders["recipient"]="77002222222"` отправляют второй номер. Это риск отправки персонализированного сообщения чужому получателю, особенно при наполнении словаря из пользовательских данных. Воспроизведено проверкой тела HTTP-запроса. Проверять имена плейсхолдеров, запрещать служебный ключ `recipient` и исключить его перезапись. Ошибки всех записей желательно выявлять до первого батча.

2. **[P1] Документированный `groups` ломает десериализацию кампании.**

   [CampaignData.cs:93](../../src/Mobizon.Contracts/Models/Campaigns/CampaignData.cs#L93) объявляет `IReadOnlyList<long>`, но API описывает CSV-строку. Ответ `{"code":0,"data":{"id":1,"groups":"12,34"}}` приводит к `MobizonException` на `$.groups`; получить остальную кампанию невозможно. В сохранённом getInfo-fixture `groups=null`, поэтому обычные тесты этого не замечают. Сохранить типизированную коллекцию, добавив конвертер CSV/null и отдельно подтверждённых вариантов. [Источник: Campaign/Get](https://mobizon.kz/help/api-docs/campaign).

3. **[P1] Обезличивание fixtures сохраняет персональные данные и повреждает JSON.**

   [Sanitizer.cs:18](../../tools/Mobizon.Net.ApiCapture/Sanitizer.cs#L18) заменяет длинные последовательности цифр, строковый баланс и кириллицу. `alice@example.com`, английский текст SMS и четырёхзначный OTP остаются без изменений. При этом `{"id":12345678}` становится `{"id":7000000XXXX}` — невалидным JSON. Оба сценария воспроизведены. [SanitizeRunner.cs:33](../../tools/Mobizon.Net.ApiCapture/SanitizeRunner.cs#L33) пишет результат прямо в fixtures, предназначенные для репозитория. Нужен обход JSON по схеме: маскирование чувствительных полей независимо от языка, синтетические значения соответствующего типа и повторный parse результата перед сохранением. Факт публикации реальных секретов этим ревью не установлен.

4. **[P2] Реальные поля `extra` кампании теряются.**

   [CampaignData.cs:81](../../src/Mobizon.Contracts/Models/Campaigns/CampaignData.cs#L81) ожидает `validity`, `mclass`, `trackShortLinkRecipients` на верхнем уровне. В [реальном capture](../../tests/Mobizon.Net.Tests/Payloads/campaign.getInfo.json) они находятся внутри `extra`. Проверка этого файла через публичный `GetInfoAsync` возвращает `Validity=null` вместо 24 часов; остальные перечисленные свойства тоже не связаны с вложенными значениями. В [матрице покрытия](../coverage-matrix.md#L29) `extra` ошибочно представлен как покрытый. Добавить типизированный `CampaignExtra` и явное отображение публичных свойств, учитывая варианты формы ответа.

5. **[P2] Список кампаний отбрасывает счётчики и провоцирует дополнительные запросы.**

   [CampaignService.cs:165](../../src/Mobizon.Net/Services/CampaignService.cs#L165) десериализует элементы в `CampaignData`; `Counters` и `CreationWay` существуют только в производном `CampaignInfo`. Документация `campaign/list` отсылает к форме `getInfo`. Воспроизведено на ответе с `counters.totalMsgNum=7`: публичный элемент не содержит счётчиков. Клиентскому приложению приходится запрашивать `GetInfoAsync` отдельно для каждой кампании. Возвращать модель, сохраняющую статистику; изменение публичного типа оформить с учётом совместимости. [Источник: Campaign/List](https://mobizon.kz/help/api-docs/campaign).

6. **[P2] Отсутствующий результат добавления получателей превращается в `AllAdded`.**

   [CampaignService.cs:383](../../src/Mobizon.Net/Services/CampaignService.cs#L383) разрешает `data:null` для любого принятого кода, а [Finalize:342](../../src/Mobizon.Net/Services/CampaignService.cs#L342) создаёт пустой результат. Для `code=0,data=null` получается `Outcome=AllAdded, Entries=null`; в многочастной операции батч также может попасть в подтверждённый прогресс. Это скрывает отсутствие ожидаемых результатов по получателям; пример README с `Entries!.Where(...)` падает. Воспроизведено. Ограничить допуск null конкретными подтверждёнными ошибочными формами ответа; успешный синхронный результат проверять отдельно.

7. **[P2] «Терпимый» конвертер контактов скрывает непустые несовместимые данные.**

   [EmptyTolerantObjectConverter.cs:33](../../src/Mobizon.Net/Internal/Converters/EmptyTolerantObjectConverter.cs#L33) отбрасывает любой массив и любой скаляр, хотя комментарий объясняет только пустые `[]`/`""`. Например, `fields.email="alice@example.com"` даёт `Email=null` без ошибки — воспроизведено на искусственном ответе, live-наличие такой формы не утверждается. Последующее сохранение контакта отправляет пустые значения для null-полей. Разрешать только подтверждённые пустые формы; непустую несовместимую форму считать ошибкой протокола либо поддержать отдельным типизированным преобразованием. Аналогично [TolerantStringEnumConverter.cs:30](../../src/Mobizon.Net/Internal/Converters/TolerantStringEnumConverter.cs#L30) теряет неизвестные строковые значения Gender/ContactType: для расширяемого словаря предпочтительнее typed value + raw string.

8. **[P2] Инструмент capture некорректно собирает TaskQueue.**

   [CaptureRunner.cs:190](../../tools/Mobizon.Net.ApiCapture/CaptureRunner.cs#L190) интерпретирует скаляр `campaign/send` как task ID без проверки кода 100, затем [строка 201](../../tools/Mobizon.Net.ApiCapture/CaptureRunner.cs#L201) отправляет `ids[0]` вместо `id`. Даже настоящий task ID запросит неверным параметром. Все три существующих taskqueue-capture содержат код 11; матрица объясняет их невалидным ID, хотя ошибочен и сам запрос. Проверять envelope/code, получать настоящий task ID от асинхронной операции и отправлять `id`. [Источник: Taskqueue/GetStatus](https://mobizon.kz/help/api-docs/taskqueue).

9. **[P2] API-ключ всё ещё попадает в URL вспомогательного клиента.**

   [RawMobizonApi.cs:18](../../tools/Mobizon.Net.ApiCapture/RawMobizonApi.cs#L18) добавляет `apiKey` в query string. Основной SDK уже отправляет ключ в теле, но capture-инструмент оставляет его доступным журналам URL прокси/диагностики. Исправить этот транспорт аналогично основному клиенту, включая валидацию HTTPS. Это замечание относится к инструменту разработки, а не к запросам основного `MobizonClient`.

10. **[P2, контрактное расхождение] Обещание сохранения срока ссылки при null не подтверждается документацией.**

    [UpdateLinkRequest.cs:27](../../src/Mobizon.Contracts/Models/Links/UpdateLinkRequest.cs#L27) обещает сохранить expiration при null. [LinkService.cs:172](../../src/Mobizon.Net/Services/LinkService.cs#L172) просто не отправляет поле. Официальное описание update говорит, что отсутствие значения делает срок неограниченным. Поэтому изменение одного комментария потенциально снимает ограничение срока жизни ссылки. Нужен live-тест на существующей ссылке с датой; затем явная семантика «сохранить / установить / снять» и согласованные DTO/XML docs. Это вывод из расхождения контрактов, не подтверждённое изменение серверного состояния. [Источник: Link/Update](https://mobizon.kz/help/api-docs/link).

**Что делать с Unknown и неполной типизацией**

- Оставить `UnknownWebhookEvent` как резерв для действительно нового типа события: сейчас он не заменяет ни один из четырёх известных DTO.
- Добавить `CampaignExtra`, сохранить статистику элементов списка и разбирать CSV групп в `IReadOnlyList<long>`.
- Известные коды результатов представить enum с возможностью сохранить неизвестное числовое значение; неоднозначный `CampaignSendResult.Id` разделить по смыслу.
- Для расширяемых строковых значений использовать уже существующий подход вебхуков: nullable enum плюс исходная строка. Не превращать весь результат в dynamic и не уничтожать незнакомое значение.
- `RecipientEntry.Placeholders` — естественный словарь строк, а `FieldErrors` — типизированный словарь ошибок: заменять их искусственной фиксированной DTO не требуется.
- Добавить контрактные fixtures с непустыми группами, extra, counters, частичными ошибками и настоящим queued task. Зелёные unit-тесты с вручную написанными JSON не подтверждают соответствие серверу.

Дополнительное открытое допущение: [WebhookDateTimeOffsetConverter.cs:39](../../src/Mobizon.Net.Webhooks/Internal/Converters/WebhookDateTimeOffsetConverter.cs#L39) трактует timestamp без offset как UTC. На проверенной странице Mobizon временная зона явно не установлена. До использования для SLA/сортировки событий нужно подтвердить её и сделать политику явной; это не отмечено как доказанная ошибка часового пояса.
