## Задача и ожидаемый результат

Исправить обнаруженные ошибки обработки Mobizon REST API, повысить безопасность и предсказуемость SDK, дополнить типизированные контракты и документацию. Приоритет — достоверность результата операции и сохранение диагностической информации без утечки содержимого SMS и персональных данных.

Этот документ передаёт контекст и план реализации. В рамках подготовки handoff изменена только документация. Другой агент не запущен; публикация пакетов, отправка SMS, создание PR и изменение внешних систем не выполнялись.

В фокусе пользователя:

1. Оптимальность и эффективность кода.
2. Developer Experience.
3. Полнота охвата API.
4. Полнота документации.
5. Безопасность.
6. Производительность.
7. Минимум нетипизированных ответов и fallback-событий.

## Ограничения и правила реализации

- Все shell-команды запускать с префиксом `rtk`, включая каждый элемент цепочки. `rtk proxy` использовать только если фильтрация действительно скрывает нужный вывод. В ревью обычный запуск тестов временно не выдавал вывод; raw-запуск помог получить результат.
- Сохранить существующие target frameworks, nullable и совместимость с C# 8.0 согласно актуальным project files. `CLAUDE.md` содержит исторические сведения; фактические `.csproj` имеют приоритет при определении targets.
- Не добавлять `dynamic`, `JObject`, универсальные публичные `Dictionary<string, object>` ради обхода конкретных несовместимых payload.
- Внутренний `JsonElement` для разбора envelope или полиморфного wire-format допустим. Публичные успешные результаты должны оставаться доменными DTO.
- Сохранить `UnknownWebhookEvent` для действительно новых event types. Его удаление ухудшит совместимость с развитием API.
- Не придумывать значения enum и поля по догадке. Опора: официальная документация, обезличенные реальные fixtures, подтверждённые API captures.
- По умолчанию не повторять автоматически операции отправки SMS, отправки кампании, создания и изменения данных. Потерянный HTTP-ответ не означает, что операция не выполнилась.
- Сохранять propagation пользовательского `CancellationToken`, `ConfigureAwait(false)` и различие между API-, transport-ошибкой и отменой.
- Изменения публичных контрактов делать преимущественно добавочными. Намеренные изменения поведения и необходимые breaking changes явно перечислить в CHANGELOG с инструкциями миграции.
- Не запускать capture-инструмент с реальными credentials и побочными эффектами для проверки обычных исправлений. Тесты должны работать без сети.

## R1 — P1: разбирать API-ошибки до успешного payload

**Файлы:** `src/Mobizon.Net/Internal/MobizonApiClient.cs`, `MobizonResponse.cs`, `src/Mobizon.Contracts/Exceptions/MobizonApiException.cs`, соответствующие transport/exception tests.

Сейчас `SendCoreAsync<T>` сначала десериализует `MobizonResponse<T>`, а затем проверяет `Code`. При ошибке `data` может содержать объект ошибок полей вместо успешного `T`. В результате ошибка десериализации скрывает API-код. Когда десериализация возможна, дополнительные сведения из `data` всё равно теряются при создании `MobizonApiException`.

**Воспроизведение:** для `Campaigns.CreateAsync` вернуть HTTP 200:

```json
{"code":1,"data":{"text":["required"]},"message":"Validation error"}
```

Текущее поведение — `MobizonException` о десериализации, поскольку ожидается `long`.

**Изменить:**

- Разделить разбор envelope и payload: проверить обязательный `code`, прочитать message, классифицировать ответ, затем разбирать успешный `T`.
- Обработку 98/99/100 оставить специфичной для поддерживающих их операций; не считать любой код 100 глобально допустимым для любого результата.
- Добавить типизированные сведения об ошибках полей в API exception. Точную форму модели выбрать по подтверждённым payload. Разумный контракт — коллекция ошибок с путём поля и сообщениями.
- Неизвестная структура error data не должна скрывать `RawCode`, `ApiMessage` и HTTP status. Не экспортировать универсальный публичный raw-объект только для такого случая.

**Приёмка:**

- Приведённый ответ вызывает `MobizonApiException` с `RawCode=1`; ошибка `text` доступна программно для поддержанного формата.
- API-ошибки с `data=null`, `[]`, объектом и строкой сохраняют API-код независимо от успешного `T`.
- Успешные scalar/object/list payload продолжают работать; async и bulk результаты сохраняют семантику.
- Неизвестный API-код сохраняется как число, а не превращается в ошибку JSON.

## R2 — P1: исключить ложный успех

**Файлы:** те же transport/envelope файлы; service tests для scalar, DTO и команд без результата.

`RawCode` имеет default 0, отсутствие `code` не обнаруживается. `SendCoreAsync` не отвергает неуспешный HTTP status при подходящем JSON.

**Подтверждено:** HTTP 500 с телом `{}` на `Campaigns.CreateAsync` возвращает ID `0` без исключения.

**Изменить:**

- Проверять обязательное присутствие и корректность типа `code`.
- Ответ non-2xx никогда не должен завершаться успехом. Если есть валидный API error envelope, можно сохранить `MobizonApiException` и HTTP status; иначе вернуть transport/protocol exception.
- Проверять наличие и форму обязательного успешного payload в зависимости от операции. Не вводить глобальный запрет `null`: часть команд и наблюдаемых list responses допускает пустой результат.
- Уточнить правила scalar ID: когда операция возвращает созданный объект/задачу, нулевой или отсутствующий ID не должен выглядеть как успешное создание.

**Приёмка:** `{}`, JSON null, отсутствующий/невалидный code, HTTP 500 с `code=0`, отсутствующий обязательный payload дают диагностируемую ошибку. Легитимные команды без data и подтверждённые пустые страницы работают.

## R3 — P1: правильный итог нескольких пакетов

**Файлы:** `src/Mobizon.Net/Services/CampaignService.cs`, `src/Mobizon.Contracts/Models/Campaigns/AddRecipientsResult.cs`, `AddRecipientsOutcome.cs`, campaign tests.

Выбор максимального `RawCode` между пакетами неверен: 0 + 99 превращается в `NoneAdded`, хотя первый пакет успешно выполнился.

**Подтверждённый сценарий:** 501 входной получатель, два ответа: первый `code=0` с успешным entry, второй `code=99` с отказом. Итог сейчас `NoneAdded`, а в `Entries` есть entry с `Code=0`.

**Изменить:**

- Агрегировать факты успеха/отказа; 0+99, 99+0 и 98+99 означают частичный успех. `NoneAdded` допустим только при полном отказе всех синхронных пакетов.
- Сохранить отключение `Replace=true` после первого пакета.
- Определить обработку ошибки/отмены после успешного пакета: подтверждённые результаты и позиция продолжения должны быть доступны; нельзя сообщать, что ничего не выполнено.
- Для транспортной ошибки явно различать подтверждённые предыдущие пакеты и текущий пакет с неизвестным исходом. Его нельзя объявлять неисполненным и безопасным для повторения.
- Для async addRecipients добавить явный признак очереди, например вычисляемый `IsQueued` по `TaskId`. Не менять существующие числовые значения enum без миграционного решения; устранить двусмысленность `AllAdded` в документации и примерах.
- Проверить отдельную multipart-ветку: согласовать разрешённые коды с подтверждённым контрактом file upload, не переносить 98/99 вслепую из синхронной ветки.

**Приёмка:** тесты комбинаций 0/98/99, границ 500/501/1001, сохранения порядка entries, `Replace`, ошибки второго пакета, отмены между пакетами и async TaskId. Для отмены сохранить совместимость с `OperationCanceledException`; механизм доступа к частичному результату документировать.

## R4 — P2: сохранять смещение ContactCards query

**Файлы:** `src/Mobizon.Net/ContactCards/ContactCardQuery.cs`, `src/Mobizon.Contracts/Services/IContactCardQuery.cs`, query tests.

`FirstOrDefaultAsync` вызывает `BuildRequest(takeOverride: 1)`, `SingleOrDefaultAsync` — с 2. Номер страницы сохраняется, поэтому изменяется offset.

**Подтверждено:** `Take(50).Page(2).FirstOrDefaultAsync()` отправляет `currentPage=2&pageSize=1`, то есть offset 2 вместо 100.

**Рекомендуемая семантика:** `Page` выбирает страницу, `Take` задаёт её размер; terminal operations не должны менять выбранное окно. Для first на явной странице безопаснее получить исходную страницу и выбрать элемент, чем менять page size. Для single явно определить проверку уникальности на выбранной странице либо во всём запросе; согласовать с текущим публичным описанием и не смешивать обе трактовки.

`CountAsync` документирован как общее число совпадений. Он должен быть независим от номера выбранной страницы; проверить поведение API для страницы за пределами результата. Не утверждать, что count вообще не получает данные: сейчас используется list с одним элементом.

**Приёмка:** стабильная сортированная fixture и сравнение `First` с первым элементом `ToList` для Page(0), Page(2), default size и Take(50). Тесты пустой/последней страницы и Single с 0/1/2 совпадениями. Если API ограничивает разрешённые размеры страниц, не строить оптимизацию на неподтверждённых pageSize=1/2.

## R5 — P2: сериализовать даты независимо от культуры

**Файл:** `src/Mobizon.Net/Internal/ContactCardExpressionParser.cs`, `ApiFormat.cs`, query tests.

В `Build` значение DateTime попадает в `value?.ToString()`. `BirthDate` и `CreatedAt` имеют тип DateTime?, поэтому результат зависит от CurrentCulture.

**Изменить:** отдельно форматировать дату рождения и timestamp через существующие invariant helpers. Формат выбрать по назначению API-поля. Не вводить неявную конверсию timezone, не подтверждённую контрактом.

**Приёмка:** один и тот же фильтр даёт одинаковое form field value при ru-RU/en-US/tr-TR; даты рождения и даты создания имеют нужные разные форматы. Культура после теста восстановлена, параллельные тесты не загрязняются.

## R6 — P2: исключить утечки payload через диагностику

**Файлы:** `src/Mobizon.Net/Internal/MobizonApiClient.cs`, converters с сообщениями об ошибках, exception tests, README.

`DescribeUnexpectedBody` включает первые 200 символов ответа в exception message. Данные становятся частью обычных application logs.

**Подтверждено:** ответ с `data.text="OTP-8421"` и неверным типом `messageId` приводит к появлению OTP в `Exception.Message`.

**Изменить:** по умолчанию оставлять HTTP status, имя операции, безопасное описание и JSON path. Проверить не только внешнее `Message`, но и `InnerException`/`ToString()`: собственные converters также интерполируют исходные значения в сообщения. Если нужна подробная диагностика, сделать её явной, ограниченной по размеру и с редактированием секретов/PII. Не обещать защиту от пользовательского HTTP body logging.

**Приёмка:** синтетические API key, OTP, телефон и email из невалидного ответа отсутствуют во всём стандартном представлении исключения. При этом можно определить операцию, HTTP status и поле с ошибкой. Удобство диагностики API ошибок сохранить через R1.

Сейчас `Validate` проверяет только непустые ApiKey/ApiUrl. HTTP endpoint допустим, ключ и данные уходят открытым текстом.

**Изменить:**

## R8 — P2: линейное накопление результатов

**Файлы:** `CampaignService.cs`, `AddRecipientsResult.cs`.

`Entries.Concat(other.Entries).ToList()` копирует все накопленные элементы после каждого пакета. Для 100 000 получателей пакетами по 500 получается примерно 10 млн копирований ссылок вместо порядка 100 000.

**Изменить:** использовать один внутренний `List<AddRecipientEntry>` и `AddRange`, при возможности с подходящей capacity. Не превращать DTO в обязательный публичный mutable accumulator. Сохранить публичную совместимость существующего `MergeEntries`, если он остаётся в API.

**Приёмка:** все результаты и порядок сохранены; структура алгоритма линейна по числу entries. Для подтверждения выигрышa использовать изолированное сравнение allocations при 500/5 000/100 000 entries без HTTP. Не добавлять нестабильные timing assertions в unit tests.

## R9 — ресурсы transport и измеряемые оптимизации

**Файлы:** `MobizonApiClient.cs`, request/stream tests.

- Явно освобождать `HttpRequestMessage` и принадлежащий ему content на success, failure и cancellation.
- Сохранить разумное владение пользовательским stream: рекомендуемый контракт — вызывающий код владеет переданным photo/recipients stream, SDK его не закрывает. Для освобождения StreamContent потребуется обёртка с leave-open семантикой или эквивалент. Добавление простого `using request` не должно неожиданно закрыть пользовательский stream.
- Согласовать с включаемыми пользователем retry для multipart: non-seekable stream нельзя молча повторно отправить как пустой/частичный файл. Это не повод включать retry записей по умолчанию.
- Оценить устранение двойной буферизации `SendAsync` → `ReadAsStringAsync` → deserialize. При переходе на `ResponseHeadersRead` сохранить общий timeout, охватывающий чтение тела: стандартный HttpClient timeout после заголовков уже недостаточен.
- Предусмотреть предел размера читаемого ответа; подобрать/document default по реальным размерам list/statistics ответов.
- В expression parser заменить компиляцию констант и простых captured fields прямым чтением узлов. Не кэшировать значение захваченной переменной навсегда: оно может меняться между выполнениями query.

**Приёмка:** disposable-тесты, caller-owned stream остаётся открытым, cancellation/timeout при медленном body работает, oversized response ограничен. Оптимизацию буферизации принимать после сравнения allocations на больших синтетических payload; если выигрыша нет или сложность чрезмерна, сохранить текущий путь и зафиксировать измерения.

- `AlphanameData.GlobalStatus`, `PartnerStatus`, `AlphanameInfo.Type` — int с явно недокументированным диапазоном. Оставить raw, пока нет достоверной таблицы; enum по догадке запрещён.
- `Campaign.Delete` и `Link.Update` вызывают `SendAsync<object>`, но не возвращают этот object пользователю. Добавить внутренний путь команды без payload; не сериализовать бессмысленный DOM ради игнорирования ответа.
- `AddRecipientsResultConverter` молча пропускает неизвестную структуру; `LinkStatsResultConverter.ToInt` заменяет невалидное/переполненное число на 0. Отличать документированные пустые значения от повреждения или изменения контракта. Для действительно некорректных значений выбрасывать диагностируемую безопасную protocol error.
- REST converters для SMS/campaign status бросают исключение на неизвестное значение, тогда как webhook SMS сохраняет nullable status + raw. Проверить возможность добавочного унифицированного контракта. Не назначать неизвестному значению существующий бизнес-статус.

### Что сохранить

- `UnknownWebhookEvent.RawData`: допустимый публичный JsonElement для неизвестного event type. Все известные события должны оставаться typed даже при неизвестном значении отдельного поля.
- Внутренний JSON DOM для `LinkStatsResultConverter`: колонки `clicksN` и `redirectsN` преобразуются в типизированные серии. Это не дефект динамической типизации публичного API.
- Осознанное исключение `userProfile` с PII можно сохранить; указать его в списке намеренно неэкспонируемых полей.

**Приёмка:** fixture-тесты новых полей, неизвестного enum value, неизвестного события, malformed data, overflow и легитимных пустых PHP-форм. Данные не исчезают молча и не превращаются в ложный успех/нулевую статистику.

## R11 — Developer Experience и resilience

- Согласовать null/empty guards публичных методов: `ArgumentNullException`/`ArgumentException` до отправки вместо случайного NullReferenceException. Не валидировать региональные бизнес-правила по предположению.
- `GetSmsStatusAsync` принимает массив без проверки лимита 100. Для существующего метода рекомендуется локальная проверка и описание лимита; автоматический batching вводить отдельным helper или после явного определения порядка, отмены и частичных результатов. Это выбор реализации, а не подтверждённая отсутствующая функция API.
- В Polly явно документировать фактически обрабатываемые transport/HTTP ошибки. `code=30` внутри HTTP 200 не попадёт в нынешний `HandleTransientHttpError`.
- Если добавляется обработка rate limit, отделить API-код 30 от HTTP 429; учитывать Retry-After для HTTP 429, bounded backoff и jitter. Сохранить запрет default retry записей. Не перечитывать body несколькими handlers без решения о владении/буферизации.
- Проверять конфигурацию retry count/delays/circuit breaker, чтобы неверные значения и overflow задержек не проявлялись только при сбое сервера.
- Для `ContactCards.UpdateAsync` выбрать единый контракт очистки полей: сейчас null простых полей отправляет пустую строку, а null Address вообще не отправляется. Устранить расхождение с обещанием full replace; безопасный вариант — точно документировать существующее исключение и дать явный способ очистить адрес.

**Приёмка:** guards до HTTP, границы 0/1/100/101 ID, тесты фактических retry для read/write, HTTP 429/API 30 если включены в scope, предсказуемое обновление/очистка контакта. Не добавлять retry как скрытый побочный эффект исправления transport.

## R12 — документация, безопасность вебхуков и coverage matrix

Обновить README, XML documentation, samples и CHANGELOG одновременно с финальными контрактами.

Обязательные темы:

- Пример NumberStopList.
- File/group addRecipients → `TaskId` → polling → завершение/отказ задачи → отправка кампании; постановка в очередь не равна окончательному успеху.
- Частичное выполнение пакетной операции и неизвестный исход текущего пакета при timeout; нельзя слепо повторять весь запрос.
- Лимиты: GetSMSStatus до 100 ID, addRecipients синхронными пакетами до 500, GetStats до 5 ссылок; polling Taskqueue не чаще 1 раза в секунду.
- Владение HttpClient/stream, timeout, cancellation, реальные условия retry.
- Точная семантика Take/Page/Count/First/Single и очистки contact fields.
- Настройка HTTPS, секретов, безопасной диагностики и опасность пользовательского body logging.
- Webhook подпись Mobizon — `SHA1(eventId|attempt|eventCreateTs|secretKey)`, не HMAC. Исправить ошибочную формулировку в ASP.NET Core endpoint XML.
- Подпись не включает data/eventType/webhookId и сама по себе не гарантирует целостность всего payload. Это ограничение протокола, а не предложение заменить алгоритм несовместимым HMAC. Объяснить HTTPS и дедупликацию по EventId в приложении; сохранение состояния остаётся ответственностью потребителя.
- Не добавлять произвольный короткий TTL webhook подписи, который отвергнет легитимные повторные доставки. Учесть документированную схему повторов.
- Неизвестное событие и неизвестное значение поля — разные случаи; показать обработку обоих без dynamic.

Создать coverage matrix с колонками:

`Модуль | endpoint | SDK method | входные параметры | поля ответа | ошибки/async формы | источник и дата | fixtures/tests | пробелы/намеренные исключения`.

Разделить статусы «подтверждено официальной документацией», «подтверждено capture», «не проверено». Не оставлять безусловное `full method coverage` для девяти модулей без соответствующих доказательств. Наличие DTO не означает, что все его поля реально проверены.

## Проверка и завершение

Базовые команды, запускать из корня репозитория:

```powershell
rtk git status --short
rtk dotnet test Mobizon.Net.sln --no-restore -m:1 --disable-build-servers -v:minimal
rtk dotnet build Mobizon.Net.sln --no-restore -c Release -m:1 --disable-build-servers
rtk git diff --check
rtk git diff --stat
```

Если restore действительно нужен, выполнить обычный restore с учётом разрешений окружения. Если RTK-фильтр снова скрывает необходимую диагностику, допустим `rtk proxy dotnet test ...` с теми же параметрами. Не оставлять зависшие собственные test processes.

Перед завершением:

- [ ] Пять подтверждённых воспроизведений стали постоянными регрессионными тестами исправленного поведения.
- [ ] P1 замечания закрыты; оставшиеся пункты имеют явный статус, причину отсрочки и оценку влияния.
- [ ] Существующие и новые тесты проходят; проверены все targets и Release build.
- [ ] Пользовательская отмена, async/bulk результаты и запрет retry записей не сломаны.
- [ ] Публичные DTO не расширены универсальными dynamic/raw payload без обоснования.
- [ ] Документация и примеры соответствуют финальному поведению, а не промежуточным решениям.
- [ ] Coverage matrix различает подтверждения и предположения.
- [ ] Производительность описана через измерения либо честно как структурное улучшение без замеров.
- [ ] Diff не содержит credentials, необезличенных captures, временных тестов и случайных изменений.

Финальный отчёт агента: что изменено, какие дефекты исправлены, какие команды и тесты прошли, изменения совместимости, непроверенные API-контракты и оставшиеся ограничения. Публикацию NuGet или реальные API-операции не считать частью проверки этого handoff.
